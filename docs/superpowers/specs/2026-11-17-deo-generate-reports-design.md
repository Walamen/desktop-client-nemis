# DEO Generate Reports — design (piece 7 of 10)

Date: 2026-11-17. Repos: desktop-client-nemis (main work) and Nemis (one web fix), branch `feat/deo-reports` in both, cut from `main`.
Web layout reference: `2026-11-14-deo-portal-web-design-reference.md` §4.8.

## Goal

Build the web's Automated Reports page (`/government/deo/reports/automated`) on the desktop. It offers four reports (Enrollment, Attendance, Academic, Staff & Compliance) for the officer's district, with a School filter, an attendance Time Period, Refresh, and PDF/Excel/Word export. It is generated offline from this device.

## What already exists (reused, not rebuilt)

**County Reports (County page 9, parts 1–5) already does all of this for a county:**
- The desktop SQLite read model `ICountyReportsReadModel` / `SqliteCountyReportsReadModel`. It ports the server's county and district report generators and takes `{ districtId?, schoolId? }`.
- The County report use cases, which stamp `generatedAt` and the district name.
- The renderer report views (`EnrollmentReportView`, `AttendanceReportView`, `AcademicReportView`, `StaffComplianceReportView`), with `isCountyWide={false}` for one district.
- The charts.
- `lib/reports/automatedReportExport.ts` and the `system:save-file` channel, which is open to every signed-in role.

**The server needs no change.** `GET /districts/:id/reports/{enrollment,attendance,academic,staff-compliance}` already call `ensureDistrictAccess`. They share `common/reports/academic-report.ts` and `common/utils/staff-qualifications.ts` with the County generators, which the desktop read model already mirrors. Web and desktop therefore agree on the rules.

**A DEO device holds one district and its county row (piece 1),** so the read model's `OWN_COUNTY` filter and its `districtId` filter select exactly the officer's district.

## Decisions (Claude's, under "decide for me")

1. **District from the session, never the renderer.** The DEO channels take only an optional `schoolId` (and a `period` for Attendance). A `schoolId` must be one of the district's active report schools; otherwise the call is refused as invalid. The device holds only its own district anyway, but the renderer must not choose the scope.
2. **Navigation.**
   - The desktop sidebar's REPORTS item becomes **Generate Reports**, linking to `/government/deo/reports/automated`, as on the web.
   - `/government/deo/reports` (the web's Reports & Compliance page, which is URL-only) becomes a ComingSoon page. It is built in the sub-pages task, following the standing "missing targets become ComingSoon" rule.
3. **Layout follows the DEO web page, not the County one:**
   - banner with Filters and Refresh buttons;
   - collapsible filter panel;
   - four report tiles;
   - export toolbar.

   The report bodies are the shared County views.
4. **Export letterhead (revised after review):** the same district header as the web DEO export: no county letterhead, because a DEO file is not a County Education Office file. "Generated by" is the officer's name.
6. **District-only scope (added after review):** the server's district generators read `{ districtId, isActive }` and nothing else. The DEO use cases therefore pass `districtOnly: true`, which makes the read model drop its own-county filter, so a district school whose `countyId` is set differently still counts. The County page never sets the flag, and the County IPC validator rejects the key, so County behaviour is unchanged.
7. **States (added after review):**
   - A failed scope load shows the error box with Retry, not an endless spinner.
   - A selected school that a sync removed from the district reads as All Schools.
   - Export is disabled while a filter change reloads.
   - Any change of report or filter clears the last export message.
5. **Web fix:** the Refresh icon spun only on the first load (`isLoading`). It now spins while a refresh runs (`isFetching`). That is the only web change, so release order does not matter.

## Known gap (accepted, as for County)

The district snapshot ships only grades and attendance of pupils currently in the district. For pupils who have moved out, the desktop counts a little fewer than the server (County memory, part 5).

## Desktop shape

- **Types:** `DeoReportQuery { schoolId? }`, `DeoAttendanceReportQuery { schoolId?, period? }`, and `DeoReportScope { districtId, district, county: { id, name, code } | null, schools }`. Results reuse `CountyEnrollmentReport` and the other County report types. `DeoApi` gains `getReportScope` and the four `get*Report` calls.
- **Channels:** `deo:report-scope`, `deo:report-enrollment`, `deo:report-attendance`, `deo:report-academic` and `deo:report-staff-compliance`. All are DEO-only and validated: an object with an optional non-empty `schoolId` (at most 64 characters) and a `period` that must be one of DAILY, WEEKLY or MONTHLY.
- **Application:**
  - `GetDeoReportScopeUseCase` returns the district, county and schools from `districtOverview` and `countyReports.listSchools`.
  - `GetDeoReportUseCase` runs the matching County report use case with `districtId` forced from the session, after checking `schoolId` against the scope.
  - No district gives a `null` district in the scope, and the reports return a validation error.
- **Presentation:** `DeoReportsViewModel` with `scope`, `enrollment`, `attendance`, `academic` and `staff`. A report loads only while it is the chosen one.
- **Renderer:** `DeoGenerateReportsPage` and the route `deo/reports/automated`.
  - States: loading ("Generating report..."), and a red error box with Retry, which the desktop adds and the web lacks.
  - Export status: "Saved to <path>" or "Export failed".
  - No district gives the usual message.
